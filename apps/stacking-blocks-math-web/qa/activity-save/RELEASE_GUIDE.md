# 9·10·11차시 저장·10층·공유 변경

## 범위와 확인된 원인

기준은 release/production의 611a9164a79556ada400ed33cd8b74436b7a6107이다.

- 9차시: 이전 화면은 생성 응답만으로 코드를 표시했고, 다시 접속했을 때 내 코드를 찾는 경로와 중복 요청 식별자가 없었다. 응답 유실 시 저장 여부를 알 수 없고 재시도하면 중복 문제가 생길 수 있었다. 생성 응답과 별도 소유자 재조회가 일치할 때만 코드를 표시하도록 변경했다. 최초 재현 검사는 세 항목 모두 실패했다.
- 10·11차시: 자동 저장 중 수동 클릭을 조용히 무시하거나 성공 문구를 지우고 반환하는 경로가 있었다. 버전/실제 내용의 재조회가 없었고 오류 원인도 뭉뚱그렸다. 단일 저장 대기열, 재조회, 충돌 비교·선택, 학생별 기기 임시 저장을 추가했다.
- 높이: 화면, 공통 검증, DB 저장 함수가 3층으로 제한되어 있었다. 새 활동 계약 2에서 0~9 높이와 실제 사용한 층의 설명만 검증한다. 기존 3층 좌표/설명은 유지한다.

이는 소스와 합성 DB에서 확인한 원인이다. 제보 학생의 특정 실패 원인이 원격 운영에서 확정됐다는 의미는 아니다.

학생 실제 경로는 PeerChallengePage / ArchitecturePage → activityApi → student-api → RPC / table이다. TeacherLessonPreview는 정적 교과 문제를 읽는 별도 읽기 전용 화면이며 학생 저장 API를 호출하지 않는다.

## 업데이트 계약

SHA-256: `40d6203df64fa371424a94a2098b21eae27e5b09206420900a5d3be999edf188`

- 기존 테이블에 nullable 열 3개와 부분 unique index 2개를 추가한다.

- 기존 행을 수정하는 backfill이나 DELETE/TRUNCATE는 없다. 공유 표식은 해당 학생이 명시적으로 공유하거나 작품을 저장할 때만 변경된다.
- 인증·RLS·student-auth·secret은 변경하지 않는다. 새 RPC는 서비스 역할만 실행한다.

각 교사는 배포된 연결 화면에서 본인 프로젝트의 업데이트 내용을 확인하고 승인한다. 제작자가 다른 교사 프로젝트를 일괄 변경하지 않는다. 자동 상태 검사가 모르는 catalog나 별도 승인 대상 데이터 차이를 발견하면 중단한다.

## 구버전 연결

- 구 Edge는 3층 설계 저장 및 버전·내용 재조회가 계속 가능하다. 서버 시각 필드가 없다면 시각을 표시하지 않으며 안내한다.
- 최대 10층과 소개서 링크는 DB 및 Edge 활동 계약 2가 확인된 뒤 활성화한다.
- 내 문제 목록/중복 방지 API가 없는 연결에서는 새 친구 문제 저장을 막고 업데이트를 안내한다. 이미 있는 친구 문제 풀이 경로는 유지한다.

## 데이터·공유 보호

- version 비교 후 저장하며, 다른 기기의 변경을 자동으로 덮어쓰지 않는다.
- 전송 성공만으로 완료 처리하지 않는다. 정상 버전과 내용, 새 계약의 서버 시각을 재조회한다.
- 작성 중 페이지를 떠나도 종료된 저장기가 새 페이지의 기기 임시 저장을 지우지 않는다.
- 11차시 완성 성공 이후에만 내보내기/공유를 제공한다. 재완성으로 기존 완료 시각·별·XP를 다시 지급하지 않는다.
- 링크는 임의의 불투명 식별자이며 로그인한 같은 학급 학생만 읽을 수 있다. 읽기 응답에 학생·학급 ID, PIN, token은 포함하지 않는다. 수정하거나 공유를 중지하면 이전 링크가 무효화된다.
- 외부 공유는 PNG/PDF 파일이다. 공개 익명 URL을 생성하지 않는다. 사용자가 설명에 직접 쓴 개인정보가 있다면 파일에도 실릴 수 있으므로 내보내기 화면에서 확인하도록 안내한다.
- PNG는 주요 소개, A4 PDF는 전체 설명과 사용 층을 여러 장에 나눠 담는다. 기기 공유 미지원 시 파일 저장으로 대체한다.

## 승격 조건 / 적용 순서

1. 지정 시험 Supabase의 접근 권한과 시험용 데이터 여부를 확인한다. 실제 학생 프로젝트로 대체하지 않는다.
2. 시험 프로젝트 catalog/함수 버전·원본·행 수를 백업한다. 알려진 설치 상태에 맞는 additive DB update → DB smoke → student-api 순서로 적용한다.
3. 합성 학생으로 9차시 생성/풀이, 10층 저장/복원, 11차시 완성·파일·학급 공유·철회·교차 학급 차단을 검증한다.
4. Unit, Chromium/WebKit, native PostgreSQL 17, Security, Typecheck, Lint, Build, CI와 코드 검토가 통과해야 운영 승격을 검토한다.
5. production PR 병합 후 Render 자동 배포만 사용하고 Frontend 및 Installer LIVE SHA를 각각 확인한다. 두 서비스를 확인하기 전 배포 완료로 보고하지 않는다.
6. 각 기존 교사 프로젝트의 업데이트는 교사 자신의 승인 경로를 이용한다.

실물 Android/iPad 검증은 브라우저 에뮬레이션으로 대체해 PASS 처리하지 않는다.

## 중단 / 복구

- 지정 시험 프로젝트 접근 실패, 원격 readback 불일치, 데이터 손실, 권한 범위 변화, 필수 검사 실패 시 merge/deploy를 중단한다.
- DB migration 실패는 단일 transaction으로 취소된다. 오류 주입으로 첫 적용의 schema/row 전체 rollback을 검증한다.
- 배포 후에는 additive DB를 삭제하거나 학생 행을 되돌리지 않는다. 저장된 10층 작품이 있는 경우 구 3층 Edge/Frontend로 단순 rollback하면 편집 호환성이 깨질 수 있으므로 먼저 forward-fix 또는 안전한 읽기 전용 대응을 검토한다.
- 보관한 이전 코드로 복구할 때도 10층 자료와 진행·보상 보존을 확인한다. production branch force reset은 하지 않는다.

## 검증 경계

로컬 E2E는 실제 페이지 + 실제 활동 handler + PGlite SQL을 연결한다. 로그인/네트워크 어댑터는 합성이다. 따라서 원격 Supabase의 Auth, PostgREST, Edge 배포 검증을 대신하지 않는다.
