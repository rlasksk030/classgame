# 데이터 증거 충돌과 교사 승인 기반 권한 복구

시작 기준: release/production `6f0a19b46e0b48ed926a66a4e0d86589e06ff384` (PR #7).
실제 교사 DB는 이 변경의 자동 검사 대상이 아니다. `tkniwelldgdlgwavyfdj`는 이름에 TEST가 있어도 실제 학생 13명의 자료가 있는 보존 대상이다.

## 두 오류의 분리

- DATA_EVIDENCE_CONFLICT: 구조 차이 0이어도 데이터 증거가 충돌할 수 있다. 원래 5개 필수 값과 기본 코드 중복·식별자 충돌·Storage 버킷·정책 충돌을 구분한다. 교사 수정 문제·학급 문제·중복 문제의 참조 수는 정보이며 양수라는 이유로 복구를 실행하지 않는다. 알 수 없는 값은 0이 아닌 미확인이다.
- UNRECOGNIZED_SCHEMA / ACL 22: 전체 비권한 구조와 원래 역할 모델을 먼저 대조한다. 과도한 권한은 정상 권한이라고 무시하지 않는다. 검증된 차이만 교사 승인 계획으로 만든다.

## 합성 DB에서 재현한 데이터 검사 결함

1. JSONB 포함 비교 `@>`는 교사가 추가한 조건이나 배열 차이까지 과거 기본 문제로 오인했다. 역사적으로 변경된 핵심 6필드를 정확 비교하며 교사 수정 내용을 덮어쓰지 않는다.
2. 동일 Storage 정책도 세션 search_path에 따라 SQL 표현이 달라졌다. 읽기 전용 요청의 트랜잭션 안에서 `pg_catalog,public`을 사용한다. 역할·함수의 지속 설정이나 정책 자체를 바꾸지 않는다.
3. 기본 문제 UUID가 다른 문제에 사용된 경우를 별도 식별자 충돌로 차단한다. UUID 삭제·교체나 참조 재연결은 하지 않는다.

이 재현 결과만으로 실제 13명 DB의 원인을 확정하지 않는다. 배포 후 인증된 기존 설치 화면의 읽기 전용 진단으로 실제 분류·건수를 확인해야 한다.

## 권한 복구 계약

설치 4단계의 ‘설치 문제 자동 진단’은 읽기 전용이다. 복구 가능한 경우 ‘복구 내용 확인’에서 대상 프로젝트, 객체, 회수·복원할 권한을 보여준다. ‘복구 승인 및 진행’을 누르기 전 DB 쓰기는 없다.

- 원래 migration으로 생성한 신뢰 가능한 ACL, 전체 구조, RLS, 함수 정의·소유자·검색 경로, 유효 권한을 대조한다.
- A: NULL ACL과 명시적 동일 PUBLIC 권한처럼 직접 권한·유효 권한까지 모두 같은 표현만 정규화한다. 데이터 증거 검사를 생략하지 않는다.
- B/C: 정확한 이력 프로필, 소유자, 역할 모델과 일치하는 객체만 최소 REVOKE/GRANT를 계획한다. grant option·외부 역할·불명확한 상속·혼합 영향은 차단한다.
- D/E: RLS·RPC 정의 등 구조 차이 또는 불확실한 상태는 승인 버튼을 제공하지 않는다.
- 계획은 서버 메모리에만 있고 5분 뒤 만료된다. 세션·자격증명·프로젝트·현재 DB 상태와 묶인다. 브라우저가 SQL이나 변경 항목을 지정할 수 없다.
- 실행 직전 권한자 접근·데이터 증거·catalog·effective ACL을 다시 확인한다. 같은 승인 ID는 한 번만 소비한다. 응답이 불확실하면 자동 재전송하지 않는다.
- 트랜잭션·DB advisory lock·앱 테이블 잠금·5초 lock timeout·60초 statement timeout을 사용한다. 승인 시 상태와 다르면 실행 전 중단한다.
- 모든 `sb_` 테이블 행(문제·학생·PIN·답안·진도·작품·평가·보상·세션 포함)을 서버 트랜잭션 안에서 전후 비교한다. 내용은 응답·로그에 내보내지 않는다. 실패하면 rollback한다.
- 전역 default privileges, RLS, 함수 본문, SECURITY DEFINER, 함수 search_path는 변경하지 않는다. 원래 migration replay, Edge 재배포, Secret 변경도 이 복구 경로에는 없다.
- 복구 후 구조·권한·자료를 재검사하고 기존 설치 상태 조회와 함수 probe를 수행한다. 서버가 INSTALLED를 확인해야 5단계를 허용한다. 실제 교사·학생 로그인은 이어지는 설치 단계에서 별도로 확인하며 OPTIONS probe를 로그인 성공이라고 보고하지 않는다.

공식 [Management SQL API](https://supabase.com/docs/reference/api/v1-run-a-query)는 OAuth `database:write` 범위를 요구한다. 해당 프로젝트의 인증된 API에서 읽기 전용 진단을 성공시킨 뒤, 승인된 SQL 실행도 같은 API의 권한 검사를 받는다. SQL 내부에서 실행자와 객체 소유권도 제한한다. 새 권한을 몰래 추가하거나 service_role을 브라우저로 전달하지 않는다.

## 데이터 복구의 경계

검사 오판은 읽기 전용 검사 수정으로 해결한다. 기존 자료를 보존하는 알려진 추가 작업은 기존 승인된 이어서 복구 경로를 따른다. 실제 중복·식별자·Storage 정책 충돌은 권한 복구로 처리하지 않는다. 영향이 미확정인 데이터는 원인과 건수를 보여주고 차단한다. 학생 기록 삭제·완료 강등·PIN 변경·임의 중복 제거를 자동화하지 않는다.

## 검증 근거와 한계

로컬 합성 13명 보존, 27개 기존 프로필, 신규 24 migration, 두 Supabase 기본 권한 fixture, ACL 22 복구, 승인 없음·만료·프로젝트 격리·동시 요청·상태 변경·실패 rollback을 검증한다. 실제 PostgreSQL 17과 전체 Chromium 결과는 PR의 최신 CI를 기준으로 한다.

실제 교사 DB의 권한 변경은 해당 교사가 설치 화면에서 계획을 승인한 뒤에만 실행된다. 합성 DB와 브라우저 모의 응답 결과를 실제 교사 DB 해결로 집계하지 않는다.
