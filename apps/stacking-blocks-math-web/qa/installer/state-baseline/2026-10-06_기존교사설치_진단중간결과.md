## 코드로 확정한 원인

1. `assessDatabaseState`는 객체 fingerprint와 기준표를 대조한다. 알려진 RELEASE 또는 정확한 history prefix의 RESUME만 실행을 허용한다. MANUAL_DELTA_REQUIRED는 별도 검토 대상으로 유지한다.
2. 차단되면 모든 migration disposition이 DRIFT_REQUIRES_REVIEW다. 따라서 status 응답의 APPLIED_BY_HISTORY + SATISFIED_BY_STATE 개수가 0이다. 화면의 **0/24는 24개 migration/DB 객체가 실제로 모두 없다는 증거가 아니다.**
3. SetupPage는 drift일 때 설치/복구/업데이트를 막고 INSTALLED일 때만 교사 확인을 허용한다. 서버도 세 경로를 409로 거절한다. 반복 클릭/재연결로 해소할 수 없는 보호 계약이다.
4. 알려진 RESUME 구조와 완전히 같은데 history가 없는 합성 PostgreSQL 상태도 차단되는 것을 재현했다. **이는 해당 교사 원인의 확인이 아니다.** catalog만으로 data-only migration 실행 여부를 증명할 수 없으므로 history 검사 제거 또는 prefix 전체 자동 인정은 하지 않았다.

## 이번 변경

- UI: drift 상태에서 migration 수치를 숨기고 기존 설치 구조 확인 필요, 자료가 없다는 의미가 아님, 삭제/새 프로젝트 생성 불필요, 비밀값 없이 제작자에게 프로젝트 ID를 전달하라는 안내를 표시한다. ACTIVE 함수 상태와 읽기 전용 설치 확인은 유지한다.
- 진단: 상태/계획 응답에 metadata-only `databaseReview`를 추가한다.
  - KNOWN_SCHEMA_HISTORY_MISMATCH: 알려진 구조와 일치하지만 history 확인 불충분.
  - REVIEWED_DELTA_REQUIRED: 기존 수동 설치 기준과 일치하나 검토된 별도 delta 필요.
  - UNRECOGNIZED_SCHEMA: 알려진 기준과 객체 차이 존재. 곧바로 위험한 drift라고 확정하지 않음.
  - 기준 이름/비교 기준 이름 및 객체별 MISSING/ADDITIONAL/CHANGED만 제공. SQL 정의·실제 row·자격증명은 반환하지 않음.
- installer 서버 별도 타입 검사에서 기존 `false | profile` 타입 문제를 발견해 동등한 undefined 분기로 보정했다. 허용 판정은 바꾸지 않았다.
- **baseline/profile 확장과 migration planning 변경 없음**. 실제 교사 catalog 없이 허용 예외나 추정 fixture를 만들지 않는다.
