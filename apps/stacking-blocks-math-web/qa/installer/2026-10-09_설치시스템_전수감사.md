## 오류와 수정

- 공개 키: 기존 PR #7의 소비된 OAuth grant 재조회 수정 유지. 이번에는 읽기 요청 최대 3회, 매회 15초(본문 포함), 250/500ms backoff 또는 5초 이하 Retry-After를 적용했다. 긴 Retry-After는 조기 재요청하지 않고 안내한다. 401/403/404는 재시도하지 않는다.
- 원격 쓰기: 120초 deadline, 자동 재전송 없음. 결과 유실 시 상태 재조회 후 복구. Auth 사용자 생성은 15초, 재전송 없음. 브라우저 요청은 일반 60초/설치 작업 10분으로 영구 대기를 끝낸다.
- 외부 오류: arbitrary upstream code/message 대신 고정 HTTP 분류만 전달한다. 폐기·비활성·다른 ref의 관리 키는 교사 계정 생성에 사용하지 않는다.
- OAuth: state/PKCE에 시작 브라우저 cookie 결합을 추가했다. grant 발급 중 revoke가 발생해도 늦은 응답이 권한을 부활시키지 않는다. refresh token은 보관하지 않고 만료 시 명시적으로 재연결한다.
- 세션: 활동 시 서버 TTL과 쿠키 수명을 함께 갱신한다. 서버 재시작으로 메모리 세션이 없어지면 기존 프로젝트 설정은 보존하고 다시 인증한다.
- 마법사: 학급 선택 복원, 학급별 PIN/로그인 확인 분리, 지연 응답 차단, 교사 세션 만료 시 5단계 재로그인 후 저장된 단계 복귀, 중복 클릭 차단.
- 학생 부분 생성: 각 성공 결과를 즉시 보존하고 재시도 전에 명단을 재조회한다. 이름만으로 합치지 않고 원래 이름·번호 쌍을 사용한다. 서로 다른 탭의 생성에 서버 idempotency를 새로 보장한 것은 아니다.
- 학급 생성 응답 유실: 설치·교사·탭별 생성 의도를 저장한 뒤 기존 API의 classCode를 사용한다. 새로고침/재시도에도 같은 코드를 쓰고, 소유 학급의 코드와 이름이 모두 일치할 때만 복구한다. 이름만 같은 다른 학급을 합치지 않는다. 별도 탭에서 의도적으로 시작한 새 학급 생성까지 같은 요청으로 간주하지 않는다.
- 설치 로그인 확인: 다른 학생의 브라우저 로그인 token을 덮어쓰거나 삭제하지 않는다.

## DB 권한 경계

22개 차이는 Supabase default grants 합성 fixture에서 ACL만으로 재현된다. 실제 문의 교사들의 ACL이 같다는 증거는 아직 없다. `TRUNCATE`를 포함한 실효 권한과 owner/role/schema context를 읽기 전용으로 대조하고 A~E만 외부 진단에 전달한다. raw ACL, SQL, 역할 이름 또는 학생 행은 응답으로 보내지 않는다.

자세한 정상 모델·승인 후 복구 절차는 `2026-10-09_설치DB권한모델과_복구경계.md`에 있다. 승인 프로필의 의미, RLS, migration과 transaction guard의 비교 대상·기대 해시는 변경하지 않는다. native PostgreSQL 17에서 발견한 정렬 locale 차이는 guard의 두 문자열 정렬에 COLLATE "C"를 명시해 제거했다. 동일 catalog의 기존 digest는 유지하며 ACL/정의/구조 필드를 제외하지 않는다. 기존 승인된 수동 설치 프로필의 역사적 권한도 이번에 몰래 변경하지 않는다. 전역 role/default privilege 자체를 새 승인 조건으로 삼으려면 별도 검증된 hosted Supabase 모델이 필요하다.

## 남은 실제 경계

1. 현재 연결된 Supabase 계정에는 안전한 별도 TEST 프로젝트와 문의 교사 프로젝트가 없다. 실제 OAuth→설치→교사/학생/학습 저장 검증은 NOT_VERIFIED. 기존 운영 학생 데이터로 대체하지 않는다.
2. project lock은 현행 단일 Node 인스턴스 범위다. Render 현재 `numInstances=1`; 서로 다른 인스턴스/재시작 중 진행 중인 원격 쓰기와의 분산 직렬화는 보장하지 않는다. scale-out 전에 별도 잠금 설계가 필요하다.
3. 원격 쓰기 응답 유실·서버 재시작은 remote catalog/history/secret/function 상태 재조회 후 복구한다. 원격 시스템까지 원자적 exactly-once를 보장한다고 주장하지 않는다.

출처: [Supabase 공개 키 조회 API](https://supabase.com/docs/reference/api/v1-get-project-api-keys). 공식 `secrets:read`/키 조회 권한, reveal 및 응답 유형을 확인했다. 실제 배포 결과와 수치는 PR #7의 최종 CI와 작업 최종 보고를 따른다.
