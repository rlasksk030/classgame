## A. 반복되는 22개 객체

실제 Render 로그에서 **4개 프로젝트**가 동일한 16개 테이블 + 6개 RPC를 `history-prefix-24` 대비 CHANGED로 보고했다. 기존 로그는 객체 해시만 포함하므로 해당 교사들의 속성별 차이는 아직 NOT_VERIFIED.

재현: 동일한 24개 원본 migration 앞에 Supabase의 기존 `postgres/public` 기본 권한(anon/authenticated/service_role의 table ALL, function EXECUTE)을 적용한 **로컬 PostgreSQL 엔진(PGlite) 합성 fixture**. 동일한 22개 객체 이름을 정확히 재현했다. 본문·RLS 변경 없이 ACL만 달라졌다. 이 결과는 원인 후보를 SQL로 입증하지만, 접근하지 못한 교사의 실제 ACL이 이 fixture와 같다는 증거는 아니다.

실효 권한을 SQL로 확인:

- 기본 fixture: 일반 테이블에 authenticated/service_role CRUD, anon 직접 권한 없음.
- Supabase 기본값 fixture: anon의 SELECT/INSERT/UPDATE/DELETE 및 TRUNCATE, authenticated TRUNCATE 등이 추가됨. PIN vault도 table 권한 차이가 있음. RLS=true만으로 같은 권한이라고 인정할 수 없음(TRUNCATE는 RLS로 보호되지 않음).
- sessions 테이블은 명시적 REVOKE 때문에 anon/authenticated 차이가 없어도 service_role의 추가 권한으로 달라짐.
- owns_class/owns_student/touch_updated_at은 NULL ACL의 PUBLIC EXECUTE와 명시적 중복 EXECUTE가 실효상 같음. 그러나 public_class_info/reset_progress/track_challenge_author의 service_role 추가 EXECUTE는 별도의 실제 권한 차이. 여섯 함수를 통째로 같다고 처리하지 않음.
- 사용자 소유 수학 DB의 읽기 전용 catalog에서도 Supabase 기본 권한의 잔여 권한을 확인했으나, 이는 수동 설치 profile이며 문의 교사 DB를 대체하는 증거가 아님.

수정:

- 27개 profile의 기대 속성별 SHA-256을 migration으로 재구성. 원래 객체 판정 해시/종류/prefix 및 migration 해시 **전부 동일**. legacy-recovery SQL도 byte-identical.
- 차이마다 속성명·SAME/DIFFERENT·digest만 전달. 정의 SQL·행 데이터·임의 원격 속성명/객체명은 로그에 노출하지 않음.
- ACL/RLS/RPC 검사, 위험 drift 차단 유지. 권한 정규화·교사 DB 권한 변경 없음.
- 후속 최소 조치: 인증된 해당 교사 세션에서 실제 속성/실효 권한을 읽고 차이를 확정한 뒤, 정말 넓어진 권한이라면 별도의 검토된 최소 권한 조정이 필요. 그 전에는 4→5 강제 이동 금지.

## B. 공개 키

코드로 확정한 결함: 첫 OAuth 바인딩에서 grant를 소비한 후 키 조회가 실패하면, 같은 세션의 POST 재시도는 키를 조회하지 않았다. 새로고침 시 프로젝트 목록도 이미 소비한 grant만 요구했다. 정상 인증 상태임에도 복구할 수 없었다.

키 선택 결함: 첫 publishable 항목의 빈 값/disabled 상태를 고려하지 않아 정상 anon 대안을 가릴 수 있었다. **운영 첫 조회 실패의 실제 upstream 형태는 기존 로그 부족으로 미확정**이며 403 또는 scope 문제로 단정하지 않는다. null legacy type과 임의 publishable 이름은 기존에도 일부 지원했다.

수정:

- 공식 응답 배열/metadata를 확인하고 활성 신형 publishable → 활성 legacy anon 순으로 선택. null/누락 legacy type 지원. 빈 값·비활성·비밀 키·service_role JWT·다른 ref JWT 제외.
- 공개 키는 선택 프로젝트 `/auth/v1/settings` GET에서 검증, redirect 차단. decode는 공개 역할 확인일 뿐 서명 검증을 대체하지 않음.
- grant 소비 후에도 같은 인증 세션으로 조회 재시도. 새로고침은 해당 세션에 바인딩한 프로젝트만 재조회. 서로 다른 프로젝트의 키/상태 공유 없음.
- 저장된 공개 키는 동일 프로젝트의 인증된 세션 + 해당 Auth endpoint의 재검증을 통과해야 재사용. 키 조회 권한이 없더라도 유효한 기존 공개 키로 연결 확인은 가능하며 DB 쓰기 권한은 기존 서버 검사 유지.
- HTTP 401/403/404/429/5xx, 배열 형식 오류, 네트워크, 사용 가능한 키 없음, Auth probe 실패를 구분. 선택한 프로젝트 유지, 성공 때만 3→4.
- 진단은 ref·고정 오류 코드·HTTP status·배열 여부·metadata 수·종류 수·disabled 수·값 필드 수·선택 가능 여부만 기록. 키/접두부/토큰/응답 원문 없음.
- OAuth App/권한 설정 변경 없음. 공식 key API 최소 scope는 `secrets:read`; 실제 403일 때만 기존 App의 권한을 확인해야 함.
