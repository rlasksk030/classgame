## [migration]

운영 migration history는 **빈 배열**이었다. schema가 없다는 뜻이 아니며 과거 수동 SQL 적용 사실과 일치한다. 이력 자동 repair 또는 기존 파일 전체 push는 이번 계획에 포함하지 않는다.

새 파일: `supabase/migrations/20261002104459_live_v4_compatibility.sql` (CLI `migration new`로 생성).

- 이 운영 프로젝트에는 승인 후 **이 파일 하나만** 별도로 적용한다. 021/022/023 등을 앞서 재실행하지 않는다. 새 빈 설치에는 기존 순차 migration 뒤의 024 역할로도 검증했다.
- 하나의 transaction, lock_timeout 5초, statement_timeout 120초. lock 획득/constraint/type 오류는 전체 rollback 후 중단한다. 조용히 timeout을 늘려 재시도하지 않는다.
- ADD COLUMN IF NOT EXISTS, CREATE TABLE/INDEX IF NOT EXISTS, 필요한 함수 CREATE OR REPLACE. 기존 정책/trigger는 삭제하지 않고 누락분만 만든다. 새 테이블 권한은 명시한다.
- 학생/PIN/session/attempt/XP/작품 row 삭제 0, 기존 true 완료 취소 0. progress updated_at을 유지하도록 해당 테이블을 잠근 transaction 안에서 named touch trigger만 잠시 중지하고 복구한다. 숨은 삭제는 없다. 파일에 있는 DELETE는 호출될 때만 실행되는 교사 초기화 RPC 정의다.
- 과거 일반 필수 attempt 증거로 완료 승격, 9차시 성공 풀이·문제 제작·10차시 초안·제출 작품에서 누락 참여/완료 추가. 반/학생 연결을 확인한다. 기존 프로젝트의 project_id는 소급 생성하지 않는다.
- 재실행 전후 모든 기존 열 데이터와 progress가 같은지 실제 PostgreSQL(PGlite)로 검증했다. 충돌하는 부분 확장 열을 넣었을 때도 전체 rollback을 확인했다.

적용 전에는 반드시 `readonly-schema.sql` 결과를 기준 snapshot과 구조적으로 비교한다. 바뀐 타입/제약/index/정책/함수, 비정상 challenge enum, 새 테이블의 부분 생성 등 예상 밖 차이가 있으면 중단하고 다시 감사한다. IF NOT EXISTS가 이름이 같은 다른 객체를 교정한다고 가정하지 않는다. 빈 history를 이유로 모든 과거 migration을 applied로 임의 기록하지 않는다. 운영용 설치 실행기는 이 프로젝트 ref를 차단하고 있으므로 우회하지 않는다.

운영 적용 여부: **하지 않음**. 전체 DB 백업/복구 가능 여부와 규모에 따른 lock 소요시간은 적용 직전 운영자가 확인해야 한다. 로컬 fixture 시간으로 운영 lock 시간을 보장하지 않는다.
